# ADR 0046：转人工工单闭环（工单表 / 意图双路径 / 与知识缺口的分界）

- 日期：2026-09-10（第 42 刀）
- 状态：接受
- 相关：ADR 0018（拒答不编造）、0024/0030/0031（知识缺口）、0036/0037（工具失败转人工）、0038（字节不动、出口必掩）、0043（受约束的 Agent 提议）、0044（两阶段写）；词条「转人工」「知识缺口」

## 背景

产品自称会把答不了的问题「转人工」，但三处都接不住：

1. **显式请求被当知识题。** `catalog_tools._HUMAN_RE` 对「转人工/真人/人工客服/找人工」的语义是**不抢**（不让目录回落抢答），落到主路径后按普通问题检索——命中就答，没命中就拒答+落缺口。顾客明说「我要人工」，系统给他一份知识缺口。**投诉/举报**则完全无识别。
2. **「已转人工」徽章是空头支票。** 消息带 `handoff=true` 时前端渲染「已转人工」徽章，但没有任何东西接住：没有工单号、没有联系人、没有时间预期。
3. **没有联系方式通道。** 顾客想被联系也没有入口。

## 决定

### 1. 新表 `handoff_tickets`（迁移 0020）——工单是「顾客要人」的产物

| 列 | 说明 |
| --- | --- |
| `id` PK | 工单号 `H-{id:04d}` 由它派生（不落列；Postgres serial 天然唯一，无并发竞态） |
| `session_id` FK service_sessions.id, **唯一** | **一个会话一张工单**：该会话第一次 handoff 事件创建，后续复用。工单描述的是「这段对话要人接」，不是每条消息一张 |
| `message_id` FK service_messages.id, nullable | 触发它的那条 agent 消息（表单挂在它下面） |
| `status` | `pending` / `resolved` 两态。**没有分派、没有坐席、没有 SLA 计时器** |
| `name` / `email` / `phone` / `note` | 联系方式捕获：`name`+`note` 必填（表单内），`email`/`phone` 可选，**整表可跳过** |
| `contact_at` | 联系方式提交时间（NULL=还没留） |
| `resolved_at` / `created_at` / `updated_at` | |

### 2. 意图双路径 → 同一个出口

- **词表快路径**：`转人工|找人工|要人工|人工客服|真人|投诉|举报`，插在 `run_ask` 分派**最前置**（订单/库存快路径之前）。**不含裸「人工」**——会误伤「人工智能」。
- **模型提议路径**：`PROPOSE_SYSTEM_PROMPT` 加第三选项，模型输出 `TOOL: handoff {}`；解析时**先识别 sentinel、不进 `TOOL_REGISTRY`**（注册表保持「三个只读工具」的精确集合契约）。
- 两者同出口：`kind="handoff"` 消息（复用既有 kind，前端零类型变更）+ **建/取本会话工单**。
- **拒答路径同样建工单**（`handoff=true` 已在前端亮「已转人工」徽章，必须真有东西接住），但**拒答消息文本不动**——`REFUSAL_CONTENT` 与既有全等断言保持。

### 3. 分界：工单是服务问题，缺口是知识问题

同一会话可能两者都有，那正是两个事实都成立：知识缺一块（治理台补文档即关闭）+ 有人要真人回复（操作者回复即 resolved）。**不合并、不互相替代**——`知识缺口` 词条的 `_Avoid_` 里「工单」照旧，含义是「不要把缺口做成工单」。
「客服工单产品」仍在 `_Avoid_`：本刀给的是**有回执的待办**，不是工单系统。

### 4. 顾客面：回执 + 联系方式，都可跳过

- **显式请求**的回复：「已记录工单 H-0001，工作时间 4 小时内回复。」+「可在下面留下联系方式，方便我们联系你。」
- **拒答**的回复文本不变；联系方式表单同样挂在下面（由 `handoff` 旗标驱动，两条路径一致）。
- 表单：姓名 + 留言必填，邮箱/电话可选，**整表可跳过**（工单已存在，联系方式只是让它可回访）。
- `complete` 载荷追加**运行时可选键** `ticket_id` / `ticket_no`，**不走 `expose_gap_id` 白名单**——缺口号是内部 ID，工单号是给顾客的回执。

### 5. 操作者面：可见、可筛、可结

会话列表加 pending 工单计数、`seg` 筛选「全部 / 待处理工单」、待处理置顶、`POST /api/service/handoff-tickets/{id}/resolve`（非法状态 409，照 `confirm_return`/`register` 先例）。

### 6. PII：字节不动、出口必掩（沿用 0038）

联系方式落库**存原文**；**操作者面出口掩电话/邮箱**（走既有 `machine_wash.redact`）；姓名不掩（操作者要称呼对方，且现有掩码粒度只覆盖电话/邮箱）。顾客回显自己的输入不掩。

## 后果

- 「转人工」从一句空话变成有号、有联系人、有预期、有结单动作的闭环；投诉/举报不再被当知识题（**语义变化：这两类不再产生知识缺口**）。
- 新增一张表与一条状态机；`run_ask` 分派多一层前置。
- **仍然没有坐席队列**——回执话术里的「4 小时内回复」是**承诺话术，不是外发能力**（不真发短信/邮件）。这一点必须在 README/closeout 如实标注，不得让它看起来像已有的通知能力。
- 已知不做（v1 边界）：工单分派/SLA/优先级/附件、顾客端工单查询页、已解决后新开第二张工单（一会话一单，解决后再有 handoff 仍复用）。
