## 2. 4–8 周成功标准

三句全部为真才算本阶段收官。面试不演示；每句必须能钉到测试、报告或脚本。

1. **发布才是权威，且在真实目录上成立。** 种子带真实 `spec_schema`；写回/闸门/发布进索引有测试；MCP 同一套 `retrieve()`，没有 publish 工具。
2. **有一份评测报告证明词法边界。** 正例 / 同义改写 / 跨商品混淆 / 应拒答 四分布；检索 recall@k + 拒答率；同义词增强必须 before/after 同一报告才许留。没有这份报告，简历不许写 RAG 质量。
3. **客服是 bounded loop，MCP 协议有自动化证据。** 模型可提议工具，代码仍做资格校验；轨迹可回放、可断言。独立脚本：检索→取正文→登记，publish 不存在，未发布搜不到。

答辩时要能指出的四件事（对着仓库，不是对着屏幕）：

- (a) loop 里模型调用 `get_order_status`，查无 → handoff，测试钉死不掉进检索编造；
- (b) 评测报告里同义改写组的数字；
- (c) MCP 脚本/测试：register 后未发布 search 空，工具列表无 publish；
- (d) 关缺口的测试：同一问法命中新 `A-xxxx·vN`，不是只改 FK。

## 3. 四条主线（都要做，有顺序）

顺序按依赖：**收口已有数据 → 让治理路径在真商品上可讲 → 尺子 → 真 RAG → 真 loop → 协议证据 → 飞轮 → 忠实度/反馈**。评测是同义词和 loop 的度量衡；飞轮和 thumbs down 要在 loop 成立之后装，否则是给 if 链化妆。

### 3.1 数据：契约在真实目录上成立，不是演示工程

痛点：91 个 Wikidata 商品 `spec_schema={}`，0010 写回 / 0019 必填闸门在这批商品上是死的——问「规格怎么进商品」会穿。`data/seed/` 目录 goal 写了但不存在；评论未挂商品。

Must（本阶段数据线只做这些）：

- 可替换种子包 `data/seed/`（或脚本一键灌）：若干带 **真实 spec_schema** 的商品（沿用类目字段：器皿材质/食品保质期/消费电子可新增 2–4 键，未知则弃权，不重开 0009）+ 已发布规格/政策/FAQ/至少 1 条带 confirmed QA 的对话。集成测试覆盖：发布写回、必填闸门、检索命中。
- 第 31 刀已入库的 Wikidata/评论继续当「多来源」证物；给其中一小撮补 schema 或挂商品，让治理路径在真名字上走通。
- 许可与出处写在种子 README（CC0 / 研究用途），口述可指。

Out：JDDC / 数据 III / 淘宝/抖音；为冷启动点穿而做的 UI；把空 schema 名字当「真实目录」。ABCD+WANDS 见第 32 刀收口，不在本刀重做。

### 3.2 评测：尺子先于改检索

痛点：`evals/golden.json` 13 条，空 key，只断言 cite/refuse/tool 形状，不断言生成文案，无同义改写组，无 recall。没有数字，「词法是刻意基线」是论点不是证据。

Must：

- golden 13 → **80–150** 条，四分布：正例 / 同义改写（保修↔质保↔三包）/ 跨商品混淆 / 应拒答（含越狱「忽略规则」）。
- runner 扩检索层：hit/miss、应引标题、拒答率；生成层 faithfulness **抽样、不挡 CI**（空 key 回归路径保持可复现，ADR 0027 不破）。
- 产出 `docs/research/rag-eval-report.md`（数字 + 失败 case + 与 bigram 软肋的关系）。
- 标题锚不锚 id（既有机制）；加 case 仍以改 JSON 为主。

Out：评测台 UI/表（0027）；微调对比；上 RAGAS 依赖只为看起来像论文。

### 3.3 真 RAG：先测边界，再零成本增强，向量按数触发

痛点：检索=全表拉回内存的字符 bigram；`score>0` 即答；无同义词；README 写 pgvector 是误导。封闭域 + 专有名词上词法仍是合理基线（BEIR / Lucene CJK），但「保修检不到质保」会当场死。

Must（评测刀之后）：

- search-time 同义词归一（保修=质保=三包；ES synonym 同构，不重建索引）。
- chunk 元数据前缀（商品名/类目，Anthropic contextual retrieval 的规则版）。
- **同一份 golden 的同义改写组 before/after**；无提升的改动回滚，禁止「我觉得更好」。
- README / 口述诚实：检索是 CJK bigram；pgvector 镜像是预留，**未用**。

Out（除非评测报告写明词法+同义词仍不够）：hybrid/pgvector、bge-reranker、换一套向量库、为简历先接 embedding。

生成侧 RAG（忠实度闸、逐句引用、thumbs down）见第 40 刀，不和检索增强混刀。

### 3.4 客服真 loop：模型提议，代码授权

痛点：`run_ask` 订单正则 → 库存词表+LCS → 检索 → 一次 LLM。模型从不选工具、从不观察工具结果再走下一步。混意图一个分支赢；工具轮不进记忆，「那个订单呢」接不上。这是 2026 面试「完整 Agent」的死亡问。

Must：

- 同一对只读工具（订单/库存）+ 检索 + 拒答，改成 **vendor `tools=` + `max_steps` 很小（2–3）** 的循环；每步观察工具结果再决定。
- **资格仍在代码**（0036/0037 精神不丢）：模型不能跳过订单号走检索顶；工具失败仍 handoff、不建缺口、不回退编造；无证据仍不调生成；citations 仍服务端定（0007）。越狱「忽略规则退款」钉测。
- 轨迹落库（步骤：想用的工具 / 参数 / 结果 / 停因为何），客服消息或 run 上可回放，评测可断言轨迹。
- 工具感知记忆：不把工具模板灌进 prompt，但留下 `{tool, arg}`，代词轮能再触发工具。
- 不引入第二套 Agent 框架（goal §7）。循环写在 `suite_api.services`，几十行，不是 LangGraph。

本刀必开 ADR：修订 0036/0037——「分派在代码」升级为「提议可在模型，授权必在代码」。0028/0018/0007/0005 不动。

Out：坐席队列；无限 ReAct；内部模块改走 MCP；运营改 planner；八个新工具一次上。
