# 第 49 刀 closeout：源录像可改绑 + 回执指名来源（`feat/clip-rebind-49`）

日期：2026-09-11。规格 `docs/progress/clip-rebind-intake.md`（八条裁决 + 九条验收 + 回退点）；依据 `docs/progress/audit-9-closeout.md` 的 **P0-2**（切片绑定不可改 + 演示自相矛盾）。**无新表无迁移**；ADR **0047 §2 追加修订段**（本刀修订第 46 刀裁决 2 的「已绑过的不改绑」）。

## 交付

| 件 | 交付 |
| --- | --- |
| 改绑端点 | `POST /api/clips/recordings/{id}/bind`（body `{candidate_ids: [int] \| null}`，null/缺省 = 全部待拣）：**允许改绑已绑的 pending 候选**（解锁点）；**已登记候选一律不动**——指定了就 409 且**一行不写**（校验先于任何写入）。返回 `{recording_id, label, bound_count}`（后端真值） |
| 列表端点 | `GET /api/clips/recordings`：created_at 降序、最多 20 条。没有它「改绑到哪一份」只能选刚上传的那份，等于把「绑错锁死」换成「只能改成最新一份」 |
| 上传回执真值 | 上传响应多一个 `bound_count`（本次顺手绑定条数，后端 rowcount）。前端此前拿「上传前的候选数」猜——第二次上传明明绑 0 条也会显示成一个数 |
| 拣选回执指名来源 | 「已登记 1 条：均已从《rebind-320x240.mp4》切出真 mp4 片段…」——回执不指名来源时，用户没法核对切的到底是哪一份（审计刀 9 的观察） |
| 前端 | 页头新增「改绑待拣候选到：〈录像下拉〉+ 改绑按钮」：勾了候选只改勾选的、没勾改全部待拣；上传后下拉自动切到新录像；列表按 id 合并（避免上传后晚到的初次拉取把新录像抹掉） |
| 并发一致性 | 拣选在 CAS 占位后 `db.refresh(candidate)` 重读绑定，且录像取不到时按 id 兜底回查——否则「切自哪一份」会与「库里绑哪一份」不一致，或并发改绑下误报「源录像不存在」（评审 P1，见下） |

## 验收（端到端，真浏览器 + 真容器）

1. 演示库原状：27 条 pending 全绑在旧录像 `acceptance-30min.mp4`（**256x144**，第 46 刀验收留下的），上传任何新录像都绑 0 条。
2. 上传新录像 `rebind-320x240.mp4`（**320x240**，30 分钟，7.0 MB）→ 回执「已上传源录像《rebind-320x240.mp4》（7.0 MB）；没有『尚无源录像』的待拣候选可顺手绑定。要用它切片段，在下面把待拣候选改绑到这一份。」（绑定数 0 是**后端真值**）。
3. 下拉自动选中新录像 → 点「改绑全部待拣」→ 回执「**已把 27 条待拣候选改绑到《rebind-320x240.mp4》**；现在拣选就从这一份切出真 mp4 片段。」（改绑前 27 条全绑在旧录像上——这一步就是审计刀 9 说的「绑错锁死」被解开。）
4. 勾选一条候选 → 「拣选登记」→ 回执「已登记 1 条：均已从《rebind-320x240.mp4》切出真 mp4 片段，转写已预置为可检索字段（待人洗）。」
5. **字节来自新录像**（两条独立证据）：新资产 267 的片段分辨率 **320x240**（旧录像切出来是 256x144）、`ffprobe` 时长 **39.000s** = 候选 7 的时窗 00:01:20→00:01:59；字节头 `ftypisom`、键 `.mp4`。
6. 门禁：集成 **892 → 903 passed / 0 failed / 0 skipped**（新增 11 例：上传真值回执 / 改绑全部 / 改绑子集 / 幂等 / 未知录像 404 / 未知候选 404 / 已登记 409 且一行不写 / 未登录 401 / 列表降序与字段集 / 列表 20 上限 / 列表与候选载荷不带 bound_count）；ruff 全过；前端 build 绿、lint 7/0。

## 评审处置（两轴独立只读子代理）

**P0 无**；两条 P1、若干 P2，已全部处置。

- **P1-1「refresh 之后取了过期快照」**：`recordings` map 是**预检时**构建的，CAS 后 `db.refresh(candidate)` 读到的新 `recording_id` 可能不在 map 里——并发改绑时（改绑提交发生在预检与占位之间）会误报 422「源录像不存在，无法切出片段」并中止拣选。评审用真 PG 复现了这条。修法：map 取不到就按 id 兜底 `db.get(ClipRecording, ...)`。这条也说明本刀自己引入的竞态确实存在（`refresh` 是对的，取法错了）。
- **P1-2 ADR 未修订**：权威决策记录 ADR 0047 §2 还写着「已绑过的候选不改绑」，而本刀把它改了。修法：按仓内先例（0037/0038）在 ADR 0047 追加「§2 修订（第 49 刀）」段，写清改绑端点、已登记候选仍不动、以及「多源仍留 Out」。
- **P2 顺手修四条**：`bound_count` 曾溢出到列表与候选行的 `recording` 里（响应模型拆成 `ClipRecordingOut` / `ClipRecordingUploadOut` 两个，回执字段只属于上传）+ 补钉测；`bind_candidates` 对空数组加显式 `return 0`（`in_([])` 会生成恒假条件静默不匹配）；列表 20 上限补钉测（原来删掉 limit 也不会红）；前端来源 label 过滤空串（免得回执出现「《》」）。

**记债**：拣选回执的来源 label 仍由前端候选状态推导（后端拣选响应不回来源 label，理论上改绑后未刷新就拣选可能指旧录像）；pick 每候选多一次 `db.refresh` SELECT（写路径小 N+1）；`in_([])` 防御虽加但无用例；录像无删除端点（旧录像留对象存储成为孤儿，第 46 刀已记）。

## 诚实披露

- **本刀修订了第 46 刀的产品裁决**（「上传即绑、已绑不改」→「上传即绑；可显式改绑」）。理由与回退点写在 intake：不改的话「绑错一份录像」是终态，而且演示稿与页面提示会自相矛盾。回退成本极低（删两个端点 + 上传响应去掉一个字段 + 前端去掉一行控件，数据层零影响）。
- **验收动过演示库**：新增 1 份源录像（`rebind-320x240.mp4`，7.0 MB）、把 27 条 pending 改绑到它、拣选出资产 267（待人洗、未发布）。旧录像与其字节仍在（没有删除端点）。
- **改绑不做留痕**：录像是切片模块自有的输入源、不是中台对象（第 46 刀裁决 1），故没有审计行；「谁在什么时候把候选改绑到哪份」查不到（`logger.info` 有服务端日志，但无中台留痕）。
- **多源仍不做**：所有候选同一份录像（单源模型），按候选分别绑定留 Out。
- 端到端证据是**本会话实测输出**（分辨率/时长/文案均为回显），未落成截图文件。
