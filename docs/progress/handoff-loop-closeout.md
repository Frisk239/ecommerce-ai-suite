## 交付

「转人工」从一句空话变成**有号、有联系人、有预期、有结单动作**的闭环：

| 层 | 交付 |
| --- | --- |
| 数据 | `handoff_tickets` 新表（迁移 0020）：`session_id` **唯一**（一会话一单）、`message_id` 锚点、`status` pending/resolved、`name`/`note`/`email`/`phone`、`contact_at`/`resolved_at`。工单号 `H-{id:04d}` **由主键派生**（不落列、不建序列、无 max+1 竞态） |
| 意图 | **词表快路径插在引擎分派最前置**（`转人工|找人工|要人工|人工客服|真人|投诉|举报`，**不含裸「人工」**——不误伤「人工智能」）+ **模型提议第三选项**（`TOOL: handoff {}`，sentinel 先于 registry 识别，只读工具注册表仍精确三个） |
| 出口 | **凡 `handoff=true` 的七处出口都建单**：词表 / 提议 / 提议被拒 / 订单查无 / 库存未设置 / 退货资格查无 / 拒答。既有各路径**文案一字未改**（精确文案断言全绿） |
| 顾客面 | 显式请求回执「已记录工单 H-xxxx，工作时间 4 小时内回复。」+「可在下面留下联系方式」；联系方式表单（姓名+留言必填、邮箱/电话可选、**整表可跳过**）；拒答路径同样挂表单（由 `handoff` 旗标驱动，两条路一致） |
| 操作者面 | 会话列表 `pending_ticket_count`（第二个 group-by 批量取，无 N+1）+「全部 / 待处理工单」分段筛选 + 待处理置顶 + 行内徽章；详情出工单面板（号码/状态/掩码联系方式+留言）+ 「结单」（ConfirmDialog，文案写明**结单不碰知识缺口**） |
| PII | 落库**存原文**（0038「字节不动」）；操作者面 `phone`/`email`/**`note`** 一律过**新增的 `redact_contact`**（出口必掩）；姓名不掩；顾客回显自己的输入不掩 |

## 超出路线图字面的一处（有意，需 Owner 知悉）

路线图只点名「显式请求 + 提议」两路建单。本刀**把拒答与工具失败也纳入**，理由是：这些出口同样 `handoff=true`、前端同样亮「已转人工」徽章——**徽章背后必须有东西接住**，否则本刀要消灭的「空头支票」仍在。配合「一会话一单」的幂等，一次会话无论怎么触发都只有一张工单，不会刷量。若 Owner 认为应严格按路线图只保留显式路径，回退点是 `_ensure_handoff_ticket` 的三处调用（订单/库存/退货资格）与拒答分支一行。

## 验收（浏览器全链，实测）

1. 顾客「我要转人工」→ 回执 **「已记录工单 H-0001，工作时间 4 小时内回复。」** + 表单（姓名*/电话(可选)/邮箱(可选)/留言*）。
2. 填表提交 → 「已记录联系方式」、表单收起；库里 `H-0001`（session 68、pending、张三、13800138000、zhang@example.com、contact_at 非空）**存原文**。
3. 新会话问「孕妇可以喝这个茶吗？」→ 拒答 + 已转人工徽章 + **表单同样在**；库里 `H-0002`（session 69、pending、无联系方式、message_id 已锚）——**拒答文案一字未改**。
4. 操作者面：筛选「全部 69 / 待处理工单 2」；两条会话置顶带「工单 1」徽章；工单面板显示 `H-0001`、姓名「张三」（不掩）、电话 **`1********00`**、邮箱 **`****@example.com`**（原文不出现）。
5. 结单 → 确认框（文案含「工单与知识缺口相互独立」）→ 待处理 **2 → 1**；库里 `H-0001` resolved + resolved_at，`H-0002` 仍 pending。
6. 筛选「待处理工单」→ 1 行（session 69）。控制台 0 报错。

## 两轴评审与处置

- **Spec 轴**（对十条裁决逐条判定）：12 条**全部满足**、无越界；工单与缺口未被合并、无坐席队列/分派/SLA/附件、回执未被写成「已发送通知」。指出 ADR §4 只列两个 ticket 键而实现多带 `ticket_contact_at`（措辞偏窄，非功能偏差）与 README 口径待同步——均已处理。
- **Standards 轴**：**P1 已修**——入口校验接受而 `redact` 覆盖不到的联系方式形态（`138-0013-8000`、`010-12345678`、`021 6234 5678`、`ab@x.co`、`a@b.cn`）会在操作者面**原样吐原文**，且 `note` 完全没过掩码。修法：新增 `redact_contact`（不动既有 `redact`，避免全局爆炸半径）——邮箱 local 与短域全覆盖；数字串（含空格/`-`/`.` 分隔、位数 ≥7）留首位与末两位；先邮箱后号码。出口对 `phone`/`email`/`note` 统一走它，并补 5 形态钉测 + 「留言里塞手机号」钉测。
  - 注：我给评审的示例里 `010-12345678` 与两个 11 位示例的星号数不自洽，实现按**位数一致**的算法统一为 `0********78`，测试同此口径（正确选择）。
- P2 已修：操作者面补**渲染留言**（必填字段此前无消费方）、删前端死字段 `ticketNo`、去掉全仓唯一的 route→route 导入（顾客提交返回自己的 ack 模型）、给 `catalog_tools._HUMAN_RE` 加注（快路径前置后该闸在引擎路径内不再触发，仅为 `catalog_intent` 纯函数契约保留）。

## 诚实披露

- **回执话术不是外发能力**：不真发短信/邮件，「工作时间 4 小时内回复」是承诺话术（ADR 0046 后果段、README 已注明）。
- **拒答路径的工单号不给顾客**：拒答消息文本一字未改，H 号只随 SSE `complete` 元数据下发（显式请求的号码在消息正文里）。两条路的顾客可见面因此不完全对称——这是裁决 2 的直接后果。
- **能力收窄（有意）**：「SO-1001 我要转人工」现在只回工单、不再顺带报告订单状态（显式要人优先于一切工具）。
- **「投诉/举报」不再产生知识缺口**：语义变化，已补钉测（此前这两类会走检索落到缺口）。
- v1 边界：工单分派/SLA/优先级/附件、顾客端工单查询页、已结单后再开第二张（一会话一单，结单后再 handoff 仍复用同一张）均不做。
