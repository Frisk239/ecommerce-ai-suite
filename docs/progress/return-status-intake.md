# 第 44 刀规格：退货确认迁移订单状态（intake + Owner 裁决）

日期：2026-09-10。分支 `feat/return-status`（基于 main `459cd30`）。依据：`docs/roadmap-product-hardening.md` 第 44 刀（纸糊#3）。**无新表**（状态集在代码收口，不加 DB CHECK）。

## 痛点

操作者点完「确认退货」之后 `orders.status` 纹丝不动——事件时间轴多了一条，状态还是「已发货」。顾客追问一句「退货进度怎么样」，工具如实渲染「当前状态：已发货」，纸糊当场穿帮。

## 现状（实测）

- `orders.status` 是自由 `String(20)`，种子只有 已发货/运输中/已签收 三值（`services/seed.py:58` `SEED_ORDERS`）。
- `return_tools.confirm_return`（阶段二）只 `orders.events` 追加确认事件，**不碰状态**（`return_tools.py:175-204`）。
- `check_return_eligibility`（阶段一）**只看下单时间窗、不看状态**（`return_tools.py:120-149`）——所以一张「已退款」的订单只要还在窗内，今天照样能被确认为「已退货」。
- 进度渲染已带状态：`render_order_answer` 输出「订单 SO-xxxx 当前状态：{status}。」——**无需改渲染**，缺的只是那个字段被真迁移。

## 裁决

| # | 裁决 | 理由 |
| --- | --- | --- |
| 1 | 合法值集 = 已发货 / 运输中 / 已签收 / **退货中** / **已退款**，定义在 `services/order_tools.py`（订单域模块） | 退货是状态机成员（调研：commerce-agents 官方 `OrderStatus` 含 `return_initiated`/`refunded`）；`order_tools` 无环依赖，`return_tools` 可安全引用 |
| 2 | **不加 DB CHECK**（不加迁移） | 订单是工具数据源、不是中台对象（0002）；演示规模下代码收口 + 钉测足够，加 CHECK 需迁移且收益低——记为债，closeout 写明 |
| 3 | **确认退货把状态迁移到「退货中」**，与事件追加同事务 | 状态迁移是「确认」这个动作的一部分；分开写会留下半成品态 |
| 4 | **加状态闸**：只有 已发货/运输中/已签收 可发起退货；已是 退货中/已退款 → 409 | 状态机不许回退：已退款的单子再退一次是错的。这也是阶段一（只看时间窗）留下的真实漏洞，本刀补上 |
| 5 | 「已退款」**不在本刀实现流程**——它只是合法值集成员（未来退款动作的归宿），本刀不新增「退款」动作 | 路线图只要求「确认退货 → 退货中」；多做一个退款动作是越界 |
| 6 | 幂等语义不动：同一确认卡二次确认仍返回 `duplicate` 409（先于状态闸判定），文案不变 | 既有契约（「该退货申请已确认过」比「状态不可退」更精确） |

## 验收（路线图钉测）

1. 确认前：`SO-2001` 状态「已发货」。
2. 确认后：状态「**退货中**」+ 事件时间轴含确认事件。
3. 问「SO-2001 退货进度」→ 回答含「当前状态：退货中」。
4. 状态集自检：`SEED_ORDERS` 的每个 status 都在合法集内。
5. 状态闸：把一张单置为「已退款」→ 资格查询仍给令牌（时间窗内）→ 确认 → **409**（而不是被改成「退货中」）。

## Out

- 不新增退款动作、不改阶段一的时间窗语义、不加 DB CHECK、不改渲染与 SSE 形状、不动顾客面。
