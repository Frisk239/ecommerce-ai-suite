## 交付

| 层 | 交付 |
| --- | --- |
| 状态值集 | `services/order_tools.py` 新增 `ORDER_STATUSES`（已发货/运输中/已签收/**退货中**/**已退款**）与 `RETURNABLE_STATUSES`（前三个）。放订单域模块、作为单一来源（`models.py` 的注释指向它，不再写死枚举） |
| 状态迁移 | `return_tools.confirm_return`：确认时在**同一事务**里既追加事件、又把 `orders.status` 迁移到「退货中」（此前只追加事件，状态纹丝不动） |
| 状态闸 | 只有 已发货/运输中/已签收 可发起退货；已是 退货中/已退款 → `status_not_returnable` → 端点 409。**闸在任何写入之前 return**（拒绝即不写：状态与事件都原样） |
| 判定顺序 | `duplicate` 先于 `status_not_returnable`——重复确认仍答「该退货申请已确认过」（既有契约文案不变） |
| 前端 | 顺手补齐：「确认退货」此前是**一击即写**（不可逆的两阶段写第二段却没有确认框），现与发布/结单同形——ConfirmDialog 确认后才执行，busy 期间框留着，失败时框也留着由 actionError 表达 |

## 验收

**钉测（路线图明确要求）**：
- `test_two_phase_return_full_chain`：确认前 `SO-2001` 状态「已发货」→ 确认后直读库为「**退货中**」+ 事件追加 → 问「SO-2001 退货进度」回答含「**当前状态：退货中**」→ 二次确认 409 且 detail 仍是「已确认过」（**钉死判定顺序**）。
- `test_confirm_refuses_non_returnable_status`：把一张单置为「已退款」→ 阶段一仍给令牌（它只看时间窗，不看状态）→ 确认 → **409 状态不可发起退货**，且**状态与事件时间轴都没动**。
- `test_order_status_sets_are_consistent`（纯函数）：`SEED_ORDERS` 的状态 ∈ `ORDER_STATUSES`、`RETURNABLE_STATUSES ⊆ ORDER_STATUSES`、「退货中」不可重复退货——防两份值集漂移。

**浏览器全链（真操作者路径）**：新会话 → 「SO-1002 我想退货」→ 资格卡（带待确认令牌）→ 点「确认退货」→ 确认框（文案写明「状态迁移为退货中、不可撤销、重复确认 409」）→ 确认 → 就地标「已确认退货」，库内 `SO-1002` 由「运输中」变「**退货中**」→ 再问「SO-1002 退货进度」→ 答「当前状态：**退货中**」+ 确认事件。**取消路径**：在 `SO-1003` 上开框后取消 → 未标已确认、库内状态与事件数原样（不写）。

- 拒绝路径只断言状态、未断言事件 → 补 `_order_event_count` 断言（裁决 4 的「都不动」此前只钉了一半）。

记债（P2，未改，均**非本刀引入**）：①确认的读-改-写无行锁，两个并发确认可各追加一条事件（状态幂等无碍，事件会重复）——需要行锁或唯一约束，留待后续；②`window_changed` 这条 409 无直接路径测试（现有只覆盖「越窗即 ineligible」与「张冠李戴 400」）；③未加 DB CHECK（订单是工具数据源、不是中台对象，演示规模下代码收口 + 自检测试足够；加 CHECK 需迁移）。

## 诚实披露

- **演示库数据动了两处**：`SO-1002` 由「运输中」按流程真迁移为「退货中」（这是本刀功能的真实样本）；另**回填**了 `SO-1001`——它有本刀之前（旧代码）写入的确认事件、状态却还停在「已发货」，与新语义「确认事件 ⟺ 退货中」矛盾，故按同一不变量回填为「退货中」（一行 UPDATE，已在此记录）。
- 确认后「关框时序」的改动（等写落地再关）**未在浏览器重跑**——上一步已用同一路径验证过确认成功与状态迁移，本次只改了关框时刻，属代码级验证；取消路径已实测不写库。
- **本刀不新增退款动作**：「已退款」只是合法值集成员（未来退款动作的归宿），界面上没有任何地方能触发它。
