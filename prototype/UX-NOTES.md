# UX-NOTES · 视觉与交互锚定

本文件两部分：前半是**调研锚定**（为什么长这样），后半是**点击验证中发现的取舍**。给 Slice Owner 搬交互进工程控制台时用。

## 一、调研锚定（2026-09-05，agent-reach 全网调研 + design-taste-frontend skill）

定位一句话：**商家侧操作台（内部工具、中等密度数据界面），不是 landing、不是 AI 聊天玩具。**
设计档位：VARIANCE 2（克制对称）· MOTION 1（几乎静态，仅 hover/active）· DENSITY 7（密度来自排版）。

| 维度 | 锚定 | 外部依据 |
| --- | --- | --- |
| 布局骨架 | 固定左侧栏（分组：数据中台靠前）+ 单列内容；列表页=筛选 tabs+密度表格；详情页=主栏可编辑 + 侧栏状态/元数据/动作 + 返回链接 | Shopify Polaris resource-index / details 模式；AdminLTE「内部工具默认固定侧栏」 |
| 密度 | 1px 细线分隔而非卡片堆砌；表格行高 ~44px；`tabular-nums` 等宽数字右对齐；密度来自排版不来自装饰 | Stripe 式表格；调研结论「表格与筛选比图表更重要」 |
| 状态语义 | **已发布 = 安静的绿**（默认态不抢戏）；待人洗 = 琥珀（等人做事）；已接入 = 中性灰；失败 = 红 | Enonic Content Studio「published 是安静的默认状态，问题才着色」 |
| 引用 | `资产ID · vN` 等宽芯片，点击直达只读证据视图；验证成本以秒计 | Perplexity / Multigrid「引用必须原位可核验」；ADR 0007 |
| 字体 | 中文系统栈（PingFang SC / Microsoft YaHei / Noto Sans CJK），正文 14px/22px，字阶 12/13/14/16/20，标题 Medium，数字可用 Semibold | Ant Design / 有赞 / Teambition 中后台字体规范；避开 Inter 默认套 |
| 色彩 | 暖灰中性（stone）+ 单一深青强调（#0f766e）；语义色独立于品牌色 | 计划硬约束（禁紫粉渐变/AI 紫）；单强调色纪律 |
| 图标 | Phosphor 图标库、线性、统一 stroke；禁 emoji | design-taste skill 图标纪律 |
| 圆角 | 全局 6px 一个档（徽章 pill 是唯一例外，作为「状态语言」） | shape consistency 原则 |
| 交互态 | 禁用发布必须写明缺什么；空态解释「为什么空、怎么不空」；失败态给出原因与出路 | 调研「每个控件至少 5 态」；Enonic 红色无效标记 |
| 窄屏 | 侧栏 → 抽屉；表格 → 卡片列表；关键路径可走完（390 实测） | 调研「移动端密集表格降级为聚焦卡片/下钻」 |

## 二、验证过程中定下的 UX 取舍

1. **两种「发布」强制分离。** 治理台「发布资产」= 主按钮 + 确认框 + 写回预告（发布后哪些表面会看到它）；运营页「投放发布」= 普通按钮 + 确认框 + 一条说明「不改变资产三态」。运营页正文用警示条说明二者区别，因为这是验收清单里「分不清」风险最高的一处。
2. **修订中的资产在列表显示双信息**：`待人洗 · 修订中` 徽章 + `线上 vN` 等宽小字。只写「待人洗」会让人以为客服断供了；只写「已发布」会让人漏掉待办。
3. **发布缺项分两类报**：「缺少必填字段」（弃权/未填）与「待确认字段」（机洗有值但没人确认）。混着报会让操作者以为要重填一遍。这是验收时发现的原案问题。
4. **拒答要显性**：拒答消息带 `拒答 · 无已发布证据` + `已转人工` 徽章，不静默。死亡三问之一必须有可见的 UI 对应。
5. **未发布内容绝不以半透明可点形式出现在检索表面**：连接层检索 0 命中时明确写「检索索引里只有已发布资产」。半透明假象比没有更糟。
6. **库存走工具条不走引用**：工具调用条（灰底、mono、参数→结果）与 RAG 引用芯片（青底）视觉分离，面试时能指出来这两类证据的差别。
7. **引用芯片点击进入只读证据视图**（`?v=N`）：显示「只读证据视图」横幅，编辑只能在待人洗版本上做。防止从客服证据直接改数据的误导。
8. **总览不做八个磁贴**：治理队列摘要条（可点数字）+ 三张闭环卡 + 其余能力一行的清单。中台靠前、连接层放「对外」分组低位。
9. **会话回流是显式动作**：「结束并回流登记」一个按钮说清楚产生什么（已接入对话资产），结束后横幅给出资产链接并强调「检索仍搜不到」。

## 二点五、视觉 v2 重做（第二轮，2026-09-05）

第一版被评「太丑」。截图诊断出的问题：品牌深青用得太胆怯（只出现在小按钮）、面板只有 1px 边框没有海拔、徽章是无细节的浅色胶囊、层级全靠字号没有重量对比、区块间距均匀无节奏——整体像「认真配置过的 Tailwind 模板」。调研 Linear 设计语言与优质 shadcn 仪表盘后落地的手法：

| 手法 | 来源依据 |
| --- | --- |
| 哑光画布（#f4f4f1）+ 白面板分层微阴影（两层 rgba 黑），海拔=阴影+边线组合 | 浅色主题正确的阴影堆叠；shadcnblocks「卡片圆角+细边+微阴影浮于哑光画布」 |
| 统计卡 = 小标签 + 26px 大数字 + 语义色图标块，可点击下钻 | 优质仪表盘通用模式「small labels with larger numeric values」 |
| 徽章 = 6px 语义色圆点 + 浅底胶囊 | 状态语义靠圆点传达，比纯色块安静且可扫读 |
| 侧栏选中态 = 浅青底 + 左侧 3px 指示条 + 图标着色；分组 11px 疏排小标 | Linear「侧栏对齐与层级密度」重设计文 |
| 主按钮内高光（inset 1px 白）+ 投影 + active 缩放 0.97 | Linear 触觉反馈与「精确几何」 |
| 分段控件替换散装 tabs；表头 stone-50/80 提存在感；行悬浮浅灰 | segmented control 惯例 |
| 对话区：双方圆头像 + 时间戳；顾客白气泡/客服浅青气泡 | 消息可归因、可回放 |
| 全局 150ms 过渡、细滚动条、选区青染、focus 环 | 「微交互要快而有目的」 |

VLM 评审结果：总览 8/10、列表 8.5/10、客服 8.5/10、详情 8.5/10，评语从「像默认 Tailwind 模板」变为「有设计系统的产品控制台」。仍然保留的克制：不加深色模式、不加渐变大色块、图表不做（数据量不支持）。

**第二轮交互复审修掉的闭环漏洞**（都已修+复测，详见 README 第二轮记录）：客服库存兜底猜商品（改反问）、登记丢原始内容导致发布后检索不到（机洗改为从 sourceContent 生成）、修订发布后回答仍是硬编码旧口径（改为从当前已发布版本内容派生）。第三个修复带出一个好的领域演示点：同一会话里修订前后的回答分别带 v1/v2 引用，正好展示「引用带版本可回放当时依据」。

## 二点七、视觉 v3：对齐 deepseek-harness / StaffDesk（第三轮，2026-09-06）

用户判定 v2 仍「AI 味」，给出两个真实项目做参照。两个子代理提取出的共同语言（StaffDesk 的 styles.css 注释直接标注继承 DSH neutral-bluish / deepseek-500）：

| 手法 | 取值 | 与 v2 的差异 |
| --- | --- | --- |
| 白画布 + 灰蓝侧栏 | 内容区 #FFFFFF，侧栏 #F9FAFB + 右侧 4% 墨线 | v2 的暖灰画布（stone）整体换冷灰蓝阶 |
| 近黑主按钮 | #0F1115，hover #43454A | v2 的深青主按钮是「AI 紫外的另一面」；DSH 系把品牌色完全请出主按钮 |
| 品牌蓝只做信息语义 | #4176E6/#679EFE：链接、选中左标、引用芯片、顾客气泡 #EDF3FE、focus、状态横幅（信息语义，低 alpha 边/底，无渐变无位移） | v2 品牌色=按钮；v3 蓝=语义 |
| rgba 墨线四档分层 | 4%/10%/12%/16% 黑 | v2 的实色 stone 边框线感更强、更「模板」 |
| hover 墨色叠加 | rgba(38,49,72,.06/.10)，不换色相 | v2 hover 换色，v3 同色加深 |
| 高密度 | 表格 ~30px 行、12.5px 字、徽章 11px/4px 圆角 | v2 徽章 22px 高 pill 偏软 |
| 细节纪律 | tabular-nums、等宽栈尾接 PingFang SC（防 Windows 宋体回退）、cubic-bezier(0.4,0,0.2,1)、active scale(0.98)、空态虚线引导框 | — |

判断「不像 AI 生成」的核心：色彩承担语义而非装饰（主按钮都不是品牌色）、hover 永远同色相叠加、边线是 alpha 墨线不是实色描边、真实产品细节（库存单位、血缘、时间戳真实日期）。VLM 评审总览/客服均 9/10。

**第三轮领域修正**（用户点名 + 子代理 15 条清单，全部修复验证）：规格字段按商品类目 schema 数据驱动（食品=净含量+保质期；器皿=净含量+材质，保温杯不再有保质期）；新增「模型配置」页（底座 CRUD、设为客服底座、与客服开关联动、导出→训练→注册全链路）；治理台登记入口；失败件人工转写前置；修订继承确认状态；运营任务 ID 贯穿失败重试；话术去承诺化；库存不报数+带单位；售后按意图选句；考核可回放+分维信号；客服会话历史条；素材可新建任务；checkbox 抵消；真实时间戳。完整清单见 README 第三轮记录。

## 二点八、客服对话区：流式输出与真实客服惯例（第四轮，2026-09-06）

调研依据：NN/g《The UX of Customer-Service Chat》（时间戳每条可见、双方消息异色、等待期进度提示）、Intercom/Zendesk 工作台（typing 指示器、消息分组、End Chat 在会话头部、quick replies）、AI 流式 UX 共识（状态机 submitted→thinking→streaming→complete/stopped；TTFT 间隙用 typing 点而非 spinner；尾部 CSS 块状光标；Stop 原位替换发送且无需确认；流式锁输入；停止保留部分文本并标记；自动跟随尾部）。

落地面：三点 typing（错峰 180ms 弹跳）+「正在检索已发布资产…」状态行（检索是本产品的真实动作，比「思考中」更诚实）；35ms/拍 × 1-3 字 ≈ 60 字/秒；光标 steps(1) 闪烁纯 CSS 不触发渲染；停止=Esc 或圆形按钮原位替换；中断标「已中断」；刷新由 load() 补全；composer 卡片化（Enter/Shift+Enter/自增高/34px 圆钮）；连续同角色分组隐藏重复头像；End Chat 移会话头部。

## 二点九、第五轮：消费者闭环补全（2026-09-06）

审查定性「闭环只在种子路径成立」后的补全原则：**中台一发布，消费者必须当即可见**——客服（retrievePublished 真检索）、考核（题库=全部已发布对话）、运营（产出引用已登记且已发布的素材/切片）、模型配置（微调开关切最新注册底座并露出导出血缘）。同时把治理闸门做成数据驱动：机洗按商品 specSchema 抽字段（可弃权），PUBLISH 在 action 层再校验——新摄入与种子同一套规则。

 IA 取舍：总览闭环卡从三列磁贴改为步进器（每行一条闭环，编号节点+连接线，全部可点），把「流程感」还给流程本身；步进节点把 /clips 与 /models 纳入入口，解决「切片和运营点不到」。

## 二点十、第六轮：演示诚实度（2026-09-06）

原则：引用变了文案就要变、状态变了卡片就要变、版本号进了血缘就不再漂。「已发布」列表口径的取舍：tab=线上在服务（publishedV，修订中资产带「待人洗·修订中」徽章在此可见），「待人洗」tab=纯新待办——修订待办不消失，只是跟着它的线上资产走；总览与列表从此同一套数字。

## 四、工程禁止照抄（产品阶段收口 · 冻结口径，2026-09-06）

**冻结口径：交互与状态机冻结，可直接指导开发；mock 大脑、假对象键、同步任务不冻结。** 本原型是交互规格，不是 FastAPI 的表结构和客服引擎。types.ts 是领域词汇的对照，不是 DDL。

| 原型里的样子 | 工程里应是 |
| --- | --- |
| `sourceContent` 字符串 + 页面上的 `oss://demo-bucket/...` | 记录只存对象键，字节在对象存储（ADR 0003） |
| 点一下机洗/生成/训练就「已完成」 | 队列：进行中 / 失败 / 重试 |
| `askService` 二元组打分检索 | 真 RAG + 商品字段工具；「规格以写回为准」这条可以留 |
| 客服 35ms 逐字 + localStorage 补全 | 只保留 thinking / streaming / stop 状态机，传输用 SSE |
| 考核追问与打分写死保温杯正则 | 从已发布对话抽题（方向对），追问与评分另做 |
| 切片登记同时暗插一条素材任务 | 产品先写明「切片→素材→中台」，否则工程只登记视频资产 |
| `dispatch(PUBLISH)` 无操作者身份 | 发布必须鉴权；回滚做成单独的移指针动作，不复用 PUBLISH |
| 路由 `path="*"` 回总览 | 要 404 |
| 登记是粘贴文本 | 工程要上传文件 |

types.ts 中的流式字段（`streaming/pendingFull/interrupted`）、`opsFailedOnce`、「训练永远已完成」均为演示专用，不得变成表结构。

已知不冻结的小不一致（工程统一）：总览与列表的待人洗口径已对齐（纯新待办）；素材「生成依据」目前取已发布前两条，工程按 brief 语义选；`detectProduct` 写死两款 SKU，工程做商品别名词典；连接层检索（子串）与客服检索（n-gram）在工程合成一套索引。

**下一刀**：工程第 1 刀 = 脚手架（FastAPI + Vite + Postgres + 对象存储接口，`docs/slices.md`）；第 2 刀厚路径 = 治理发布写回 或 客服带引用（原型里这两条最完整）。实现以 `CONTEXT.md` + ADR + 本原型交互为准。
